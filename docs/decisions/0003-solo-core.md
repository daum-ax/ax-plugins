# 0003 — 혼자 작업하는 사람 기준으로 핵심 축소 (2026-09-26)

**문제.** 0.1.0 은 "비개발자끼리 협업하는 팀"을 가정했다(`git-collab.md` §0). 실제 핵심
사용자는 혼자 바이브코딩하고 혼자 사내 배포 포털에 배포하는 사람이다. 그 사람에게 어려운
것은 git 인증·커밋·push·버전 남기기 네 가지인데, 잘 안 쓰는 스킬 14개가 목록에 섞여 무엇을
눌러야 할지 헷갈리게 했다. 또 `push` 는 main 대신 작업 브랜치에 올리고 합치기는 `pr` 에
맡겼기 때문에, `pr` 을 안 쓰는 사람의 결과물은 브랜치에 흩어진 채 main 에 모이지 않았다.

**결정.** 14개 → 6개 (`welcome` `github-login` `commit` `push` `release` `status`).

- `push` 는 지금 브랜치에 그대로 올린다. 보호 규칙(`GH006`)이나 먼저 올라온 작업
  (`! [rejected]`)을 만나면 "협업 저장소"라는 신호로 보고 멈춘다 — 자동 브랜치 생성·자동
  pull 을 하지 않는다. 원격이 없으면 `gh repo create --private` 로 만든다. 저장소 소유자
  (개인/조직)는 배포 포털의 규칙이라 적지 않았다.
- 새 `release` 는 `vN` annotated 태그를 붙여 그 태그만 push 한다. 포털은 "배포 커밋을
  가리키는 태그가 있을 것"만 요구하고 이름은 보지 않으므로 포털 전용 규칙이 없다. semver 를
  쓰지 않는 것은 비개발자에게 마이너/패치 구분을 묻지 않기 위해서다.
- `undo` 는 파일 되돌리기(`/rewind`)와 배포 되돌리기(포털 롤백)로 대체되고, `explain` ·
  `handoff` · `record` 는 Claude 기본 능력으로 충분하며, `dev-up` 은 유지비가 가장 컸다
  (본문 256줄 + 레시피 146줄). 서버에서 뜨는지는 포털이 판정한다.

**협업 팩 보관.** `pr` · `review-pr` · `pull` · `fix-conflict`, `push` 의 브랜치 흐름(0.1.0
Step 3·6), `welcome` 의 clone 흐름(0.1.0 Step 2.5)은 0.1.0 커밋(`ax-skills/v0.1.0`)에 그대로
남아 있다. 후속 플러그인 `ax-collab` 을 만들 때 거기서 되살리고, `plugin.json` 의
`dependencies` 로 `ax-skills` 에 의존하게 한다. `git-collab.md` 의 협업 전용 항목은 § 번호를
지키려고 지우지 않고 "협업 팩 전용"으로 표시했다. §3.5(이름 겹침)는 협업 전용이 아니라
남은 스킬에도 적용되므로 표시하지 않았다.

**계획서와 달리 한 것.** `github-login` 은 "변경 없음" 대상이었지만 사라진 clone 흐름과 옛
`GH006` 안내를 가리키고 있어 그 몇 줄만 고쳤다. `welcome` 은 원격이 없어도 github.com
로그인을 확인한다 — 새 `push` 의 저장소 생성에 그 로그인이 필요하다. `release` 는 태그
push 가 `already exists` 외의 이유로 실패하면 방금 만든 로컬 태그도 지운다 — 남겨 두면 다음
실행의 "이미 버전이 붙어 있으면 멈춤" 판정이 올라가지 않은 태그를 보고 거짓으로 멈춘다.

**남은 것.** 저장소를 어디에 만들어야 포털이 읽을 수 있는지, 배포 연결 플러그인을 이
marketplace 에 둘지는 포털 쪽 결정이다(계획서 §6).
